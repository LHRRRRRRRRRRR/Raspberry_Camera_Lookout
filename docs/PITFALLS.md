# 踩过的坑

这份文档记录的是**实际调试过程中撞出来的问题**，每条都附了现象和根因。
如果你在复用这套代码，这里能省你几个晚上。

---

## 1. `main` 流默认是 4 字节/像素，不是 YUV420

**现象**：录制出来的 `clip.mp4` 有 449MB（10 秒），画面全是垃圾。

**根因**：

```python
# 看起来没问题，实际得到 1920×1080×4 = 8,294,400 字节/帧
pc.create_video_configuration(main={"size": (1920, 1080)})
```

`create_video_configuration` 的 `main` 默认格式是 **XBGR8888**（4 字节/像素），
而 ffmpeg 按 `yuv420p` 只吃 `1920×1080×1.5 = 3,110,400` 字节。
每帧差 5MB，ffmpeg 把错位数据当图像编码。

**修复**：显式写 `format="YUV420"`，并在喂帧前断言长度：

```python
main={"size": (1920, 1080), "format": "YUV420"}
...
if len(frame) != w * h * 1.5:
    log.warning("帧长度异常，丢弃")
    continue          # 宁可丢帧也不要喂垃圾
```

**教训**：管道要断言长度；子进程的 stderr 绝对不能丢进 `DEVNULL`
（我们就是这样瞎了七八轮）。

## 2. `RGB888` 和 `YUV420` 的色彩不一致

**现象**：同一台相机、同一场景，`RGB888` 出来的木头地板是灰蓝色，`YUV420` 是正常的木色。

**根因**：PiSP 的 RGB 输出路径与 YUV 路径的色彩处理不同，
且 libcamera 的 `RGB888` 在 V4L2 层映射成 `BGR24`（内存里其实是 B,G,R），
各种约定混在一起极易搞错。

**修复**：全程走 YUV420，**不做 RGB 转换**：

- 录像：I420 平面数据直接 pipe 给 `ffmpeg -pix_fmt yuv420p`
- 预览：I420 直接封成 JPEG（PIL 的 `YCbCr` 模式），等于原样搬运
- 运动检测：直接用 Y 平面（它本来就是灰度）

**顺带的好处**：省掉一次全图转换，CPU 更低。

## 3. ESP32 重连时要先发 `STREAM 0`

**现象**：服务重启后，日志一直是 `ESP32 无响应（PONG 超时）`。

**根因**：ESP32 在上一轮连接里还开着推流，串口缓冲塞满了旧的 JPEG 二进制。
Pi 发 `PING` 后读到的"下一行"是视频数据，永远看不到 `PONG`。

**修复**：连接后先发 `STREAM 0`，排空缓冲，再握手：

```python
ser.write(b"STREAM 0\n")
time.sleep(0.5)
while ser.in_waiting:      # 排空
    ser.read(ser.in_waiting)
```

## 4. 逐字节读串口会把自己读超时

**现象**：ESP32 偶尔"超时重连"，但画面其实一直在来。

**根因**：用 `ser.read(1)` 逐字节找帧头。串口跑到 160KB/s 时，
这个 Python 循环根本跟不上，2 秒超时被吃光。

**修复**：按块读 4096 字节进缓冲区，在内存里 `bytearray.find()` 找帧头。
顺带解决了"JPEG 二进制里偶尔出现换行符导致错位"的问题。

## 5. 信号处理函数里 `shutdown()` 会死锁

**现象**：`systemctl stop vision` 卡住 90 秒，最后被 SIGKILL。

**根因**：

```python
def _bye(signum, frame):
    srv.shutdown()          # ← 死锁
```

信号处理函数跑在**主线程**，而 `serve_forever()` 也占着主线程。
`shutdown()` 要等 `serve_forever()` 退出，`serve_forever()` 又在等信号处理函数返回。

**修复**：另开线程去关：

```python
threading.Thread(target=srv.shutdown, daemon=True).start()
```

## 6. 事件结束时仍在喂帧，`close()` 会被活活喂死

**现象**：录制时长到了，事件却永远不结束，文件一直变大。

**根因**：`close()` 在队列满时"取一个塞一个"，而采集线程因为
`events.busy` 仍为 `True` 还在不停喂——消费者已经退出，生产者还在灌。

**修复**：`Recorder` 加 `closed` 标志，`feed()` 在关闭后直接返回。

---

## 7. Lux 读数受当前配置影响，日夜切换会打摆子

**现象**：日志里 1 秒内 `切换配置 → night` 又 `切换配置 → day`，反复横跳。

**根因**：切到 night 会改曝光和增益 → Lux 读数跟着变 → 立刻又满足切回 day 的条件。
正反馈。

**修复**：加"最短驻留时间"（默认 30 秒），切一次之后短期内不再切。

## 8. NoIR 没有 IR-cut，白天偏色是物理问题

**现象**：白天画面洋红/青绿，白平衡怎么调都有一边不对。

**根因**：NoIR 拆掉了红外截止片，近红外混进所有通道。而且不同材料反射
红外的能力差别很大——棉布、皮肤、白漆各自跑偏，**空间上不均匀**。

实测同一帧：

| 区域 | R/G | B/G | 偏向 |
|---|---|---|---|
| 墙面 | 1.11 | 0.67 | 偏黄红 |
| 衬衫 | 0.93 | 1.36 | 偏蓝青 |
| 全图平均 | 1.04 | 0.95 | **接近中性** |

整幅平均是中性的，所以自动白平衡认为"已经平衡了"不动；
而两组物体的偏色方向相反，**任何单一增益都不可能同时修好**。

**结论**：这是物理问题，软件无解。要么装可拆 IR-cut 滤镜（白天装、夜里拆），
要么把灯换成 LED 白光（红外输出低一个数量级）。
夜间直接转黑白——红外夜视本来就没有颜色信息。

## 9. 相机装反了

**现象**：画面上下颠倒。

**修复**：`Transform(hflip=1, vflip=1)`，在 ISP 里做，不耗 CPU。
注意 `Transform` 的第一个位置参数是 `rotation`，不是 `hflip`——
`Transform(1, 1)` 会抛 `ValueError: Invalid rotation`。

## 10. 120fps 只在小分辨率下可行

实测（Pi 5 / IMX708）：

| main | lores | 结果 |
|---|---|---|
| 1920×1080 | 1280×720 | 55.8 fps（传感器该模式上限 56） |
| 1280×720 | 640×360 | **120.3 fps** |
| 960×540 | 640×360 | **120.3 fps** |

1080p 下传感器最多 56fps。要真 120 必须把 lores 降到 640×360。

**另一个坑**：120fps 采集时，如果每帧都复制一份主图，
就是 166MB/s 的 memcpy，会把采集循环拖到 11fps。
必须按 `record.fps` 节流——否则录出来的时长也不对（变成慢动作）。
